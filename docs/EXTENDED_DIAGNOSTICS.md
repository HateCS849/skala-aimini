# 추가 진단 계약과 판정 범위

## 정합성

`integrity.enabled`와 `mode: integrity`로 전용 검사를 실행합니다. `mode: load`에서 integrity만 켜면 회복 단계 뒤에 정합성 검사를 추가합니다. 계획의 setup·mutation·snapshot 요청을 사용자 앱에 맞게 바꿀 수 있습니다.

- `{{experiment_id}}`: 실행/검사/반복별 고유 데이터 범위.
- `{{request_key}}`: 재고 검사는 요청마다 다른 키, 중복 검사는 모든 요청에 동일한 키.
- setup: 테스트 데이터 준비 요청. 기존 데이터를 초기화하는 계약이 아니며, 예제는 이미 있는 범위의 재설정을 409로 거절합니다.
- snapshot: GET 상태 조회. stock/orders/unique_keys의 실제 숫자 필드를 연결합니다.
- mutation: 주문 등 실제 변경 요청. 거절 응답 409도 예상 상태로 설정할 수 있습니다.

재고 음수, 초기 재고 이상의 주문, 주문 수×수량과 재고 차감의 불일치를 확인합니다. 중복 검사는 동일 키를 반복했을 때 실제 새 주문과 고유 키가 각각 정확히 1개여야 통과합니다. 전부 거절하거나 상태 필드가 누락되면 통과하지 않습니다. 주문당 수량 설정과 실제 mutation 본문 수량은 일치시켜야 합니다. 비동기 처리 앱은 settle 시간과 상태 조회 계약을 해당 처리에 맞게 설정해야 합니다.

기존 API만으로 결과를 볼 수 없다면 테스트용 읽기 전용 상태 조회 어댑터가 필요합니다. HTTP 성공 코드만으로 실제 저장 정합성을 추정하지 않습니다. 실제 결제 취소·재고 복구·운영 주문 정리는 자동 실행하지 않습니다.

## 추가 장애 제어 필드

예제/제어 어댑터 POST에 다음 필드를 추가로 지원합니다. 설정한 확장 필드만 전달하므로 기존 어댑터의 기본 실험 계약은 유지됩니다.

```json
{"external_behavior":"malformed","db_delay_ms":300,"db_lock_seconds":3,"cache_unavailable":true}
```

`external_behavior`는 normal/malformed/disconnect입니다. 예제의 disconnect는 실제 HTTP 스트림을 중단합니다. DB 지연은 실제 연결을 잡은 상태의 지연, DB 잠금은 SQLite 쓰기 트랜잭션 잠금입니다. PostgreSQL의 행 잠금/데드락/쿼리 지연을 자동으로 재현하는 구현과는 구분합니다.

## 실제 Redis

전용 Redis는 127.0.0.1:16379에 실행하며, 예제의 TCP 게이트 8732를 통해 GET/SET 합니다. gate는 burstguard 접두사의 키만 중계하고, 해당 버전의 cache_unavailable이 켜지면 실제 TCP 연결을 닫습니다. Redis 서버 자체를 중지하거나 다른 애플리케이션의 키를 지우지 않습니다.

변경 전은 캐시 오류를 사용자 요청 실패로 반환합니다. 변경 후는 DB 대체 경로와 프로세스 내 짧은 TTL·동시 요청 합치기를 사용합니다. Redis 중단 시간의 재고 정확성, 분산 락, 세션 저장소 복구까지 검증하는 것은 아닙니다.

## 추가 계측

JSON metrics 어댑터에서 다음 숫자 필드를 선택적으로 수집합니다.

| 필드 | 의미 |
|---|---|
| provider_attempts | 외부 HTTP 시도 누적 수 |
| logical_auth_requests | 논리 로그인 요청 누적 수 |
| cache_errors / cache_hits | 캐시 실패/적중 누적 수 |
| db_reads / db_lock_errors | DB 읽기/쓰기에 대한 잠금 실패 누적 수 |
| process_rss_bytes | 현재 상주 메모리 바이트. 최대 RSS와 구분 |
| heap_used_bytes | 실제 추적 힙 사용량. Python 예제는 tracemalloc, Spring은 jvm.memory.used의 area:heap |
| open_fds | 열린 파일/소켓 등 FD 수 |
| process_threads | 프로세스 스레드 수. Python 예제는 Python 스레드, Spring 어댑터는 JVM live threads |
| uptime_seconds | 현재 프로세스 기동 이후 초 |

3건 이상의 논리 요청 표본에서 외부 시도 증가량/논리 요청 증가량이 3을 초과하면 재시도 증폭을 표시합니다. 누적 카운터가 재시작으로 감소한 경우 해당 구간 비율은 미확인입니다. 계측이 없으면 호출 횟수를 추정하지 않습니다.

## 재시작

실험실이 subprocess로 실행한 8731 예제에만 허용합니다. 프로세스 핸들을 직접 보유하며, 기존에 실행된 프로세스가 해당 포트를 쓰고 있으면 시작을 거절합니다. 외부 PID를 받아 종료하지 않습니다.

강제 종료 또는 정상 종료 후 실제 기동·health 확인·부트 ID 변경을 기록합니다. 선택한 GET snapshot의 숫자 필드를 전후 비교해 기준 데이터 보존을 확인합니다. 데이터가 변하지 않아야 하는 기준 리소스를 지정해야 합니다. 부하가 동시에 수정하는 주문 수를 불변 기준으로 지정하면 그 변화와 유실을 구분할 수 없습니다. 예제 시나리오는 별도의 기준 주문을 준비하고 부하는 조회만 수행합니다.

사용자가 중단하더라도 이미 시작한 예제 재기동은 완료한 뒤 종료합니다. 이는 테스트 프로세스를 복구하기 위한 처리입니다. 실험실 자체의 강제 종료나 컴퓨터 종료까지 복구를 보장하지는 않습니다. 실제 Kubernetes 롤링 배포·다중 인스턴스 트래픽 분산·메시지 유실 검증은 포함하지 않습니다.

## 장시간 추세

최소 관찰 시간(기본 30초)과 8개 이상 지표가 필요합니다. RSS와 힙을 각각 비교합니다. 운영체제 압축·스왑 때문에 RSS가 감소해도 살아 있는 힙 데이터는 증가할 수 있습니다. 초기 20% 표본을 제외하고 나머지 3개 구간 평균을 비교합니다. 세 구간이 연속 증가하면서 절대 기준(기본 메모리 16MiB, FD 16개, 스레드 8개)과 상대 증가 20%를 함께 넘으면 증가 징후로 표시합니다. 누수 확정이나 원인 코드 판정은 아닙니다. 짧은 실행·누락된 지표는 미확인입니다.

최대 부하 단계 1시간, 기본 요청 예산 50,000건이며 설정으로 최대 200,000건까지 허용합니다. 예산에 도달하면 설정 시간 전체 부하가 유지되지 않았다는 제한을 남깁니다. 완료 표시가 1시간 관측을 보증하는 의미는 아닙니다. 지표는 단계 길이에 따라 간격을 늘려 약 1,800개와 마지막 표본으로 제한하며, 진행 중 요청의 종료 시간은 추가될 수 있습니다.
